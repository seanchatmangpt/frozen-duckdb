# Receipt Sealing: GATE-V Verdicts into the Evidence Substrate

Revision-2 §5, operationalized. How a GATE-V-nn court verdict seals into
frozen-duckdb's existing receipt substrate — the same machinery the
5 native gates already use today.

## Standing summary

| layer | standing | evidence |
|---|---|---|
| 5 native gates seal into `scripts/verify-evidence.ttl` | ALIVE | `make verify-gates` run of 2026-10-19 (below) |
| GATE-V-nn rows as `ver:RequiredCheck` facts | PROPOSED | this doc; unimplemented |

## The ALIVE part: native gates already seal this way

`scripts/verify-gates.sh` is GENERATED by `ggen sync run` (rule
`render-verify-gates` in `ggen.toml`) from `schema/verify.ttl` via
`schema/verify-gates.rq`. Its header states the law:

> Consequence — edit schema/verify.ttl (the ver:RequiredCheck facts), never
> this file.

Sealing chain, all ALIVE:

1. **Run** — `run_gate <name> <cmd> <red-standing>` executes each command from
   `schema/verify.ttl` and captures the REAL exit code.
2. **Bind to subject** — `git rev-parse HEAD` / `HEAD^{tree}` stamp
   `ver:subjectHead` / `ver:subjectTree` into the evidence graph, so the
   verdict is bound to the exact commit, not to a wall-clock.
3. **Bind to graph** — `payload.graph_hash` from `.ggen-v2/receipt.json`
   becomes `ver:verifiedGraphHash` on every `ver:Check`.
4. **Seal** — the `ver:Check` rows are written to
   `scripts/verify-evidence.ttl` with `ver:exitCode`, `ver:tool`,
   `ver:recordedAt`. Nonzero exits propagate to a nonzero script exit with
   `STANDING: BUILD_BROKEN`/`BLOCKED`; all-green prints
   `STANDING: ALIVE — all N gates green`.
5. **Countersign** — `ggen receipt verify` recomputes the BLAKE3 chain over
   `.ggen-v2/receipt-log.jsonl` and validates `signature_hex`;
   `scripts/verify_publish_receipt.py` additionally enforces the
   `ggen_sync_receipt` contract from `generated/receipt_contract_matrix.json`
   (Gates 1-3: `receipt verify` valid + signature_valid, mandatory contract
   fields present, `receipt history` full-chain replay).

## The PROPOSED part: GATE-V-nn rows

Each GATE-V-nn court gets one `ver:RequiredCheck` in `schema/verify.ttl`:

```turtle
fdv:req-gate-v-01 a ver:RequiredCheck ;
    ver:name "gate-v-01" ;
    ver:checkCommand "<court command>" ;
    fdv:redStanding es:BLOCKED ;
    rdfs:comment "GATE-V-01 court: <what the verdict certifies>." .
```

Once present, `ggen sync run` re-renders `scripts/verify-gates.sh` and the
Makefile `verify` target, and the court command joins the seal battery with
zero projection edits — the same run_gate/bind/seal/countersign chain as the
natives. Each sealed GATE-V verdict additionally carries a court-artifact
digest: the court's own receipt (JSON/exit-code output) is hash-addressed and
its digest recorded in the `ver:Check` row's `ver:tool` string or an
adjacent `fdv:courtArtifactDigest` literal, so the verdict can be replayed
against the exact artifact, not just re-run. Seal order is fixed:

1. `make gates` (sync + genesis-check) — projections current
2. court commands run and seal as `ver:Check` rows
3. `scripts/verify_publish_receipt.py` — chain + signature + contract gate
4. release certification cites `ver:subjectHead` of the sealed graph

Sealing is against the exact commit SHA before release certification: the
`ver:subjectHead`/`ver:subjectTree` stamps plus
`ver:verifiedGraphHash` tie every verdict row to one commit and one closure
hash. A verdict row whose HEAD stamp differs from the release candidate SHA
is not admissible as release evidence.

## Extension point

Author `ver:RequiredCheck` facts in `schema/verify.ttl` (consumer policy per
`packs/ggen-verify-pack`, which ships zero RequiredCheck individuals by
design). `schema/verify-gates.rq` is the single row-source both projections
select from. Do NOT hand-edit `scripts/verify-gates.sh`,
`scripts/verify-evidence.ttl`, or the Makefile — all three are generated and
`make genesis-check` flags drift.

## Falsifier

A GATE-V verdict claimed as release evidence whose `ver:Check` row is absent
from `scripts/verify-evidence.ttl` at the release-candidate HEAD, or whose
`ver:verifiedGraphHash` differs from the current `.ggen-v2/receipt.json`
`payload.graph_hash`, refutes the seal. Second falsifier: a GATE-V court
command added anywhere other than `schema/verify.ttl` (hand-edited
projection) — `make genesis-check` must flag it; if it passes genesis-check,
the gate is vacuous.
