## (3) MIT crate vs MIT header — interaction

Since both our code (`license.workspace = true` → MIT in all three crates:
`crates/frozen-duckdb/Cargo.toml:5`, `crates/frozen-duckdb-builder/Cargo.toml:5`,
`crates/frozen-duckdb-sys/Cargo.toml:5`) and the vendored headers are MIT, there
is **no MPL larger-work analysis needed**. Standard practice for MIT-in-MIT:

- retain the upstream copyright + permission notice in redistribution
  (`crates/frozen-duckdb-builder/LICENSE-DUCKDB.md` exists as the attribution
  carrier — but see correction below),
- keep the "AS IS" warranty disclaimer,
- that is the entirety of the MIT obligation. No source-availability duty, no
  file-level copyleft.

**Correction to the existing attribution file** (informational, this lane does
not edit it — owner is AD8/package lane): `LICENSE-DUCKDB.md` currently states
the vendored headers are "licensed under the Mozilla Public License, Version 1.1"
at "pinned tag `v1.5.5`". Both claims are stale for the v2.0.0 window: the
pin is `b6013f7` (2.0.0), and v1.5.5 upstream LICENSE is MIT (fetched above,
exit 0). Recommend AD8 regenerate that file with the MIT notice + upstream SHA
`d54cbbe3df17e8e5ce68312f483b4155836112aa`.

## (4) What similar projects do (cargo packaging convention)

Since the headers are MIT, the cargo/crates.io convention for vendored MIT
headers is:

1. **Attribution carrier file** per vendored-artifact crate (what
   `LICENSE-DUCKDB.md` already does structurally): name the upstream project,
   the exact pin, and the license, shipped inside the `.crate` so
   `cargo package`/`crates.io` distribute it.
2. **`include = [...]` / `license` + `license-file`** — crates commonly declare
   `license = "MIT"` and ship the third-party notice alongside; cargo packs all
   files under the crate root, so a `vendored-headers/` + notice file inside
   `frozen-duckdb-builder` satisfies "retain the notice" on redistribution.
3. **Comparable projects**: `libduckdb-sys` (the upstream-adjacent duckdb-rs
   binding crate) ships DuckDB headers with MIT `license` in Cargo.toml and an
   upstream notice; `duckdb-rs` itself is MIT. Other header-vendoring crates
   (e.g. `libsqlite3-sys`, MIT-with-notice for its bundled SQLite) follow the
   same pattern: bundle the notice, declare the crate license for *our* code,
   keep them separate.

(Had the headers been MPL 1.1, the standard practice would instead be: retain
the MPL notice per file, state source availability for those files
(https://mozilla.org/MPL/1.1/), and treat our crate as a "Larger Work" under
MPL 1.1 §3 — the file-level copyleft stays attached to the headers only. This
paragraph is informational context only; it does not apply at the current pin.)
